## 答え

1. **Pythonから使うなら常にimport、シェル・他言語からなら `scripts/`。** 数百件を一度に読み書きする用途でも、シェルのスクリプトを繰り返し起動しない。操作別の関数に無いエンドポイントも `notion_request` で叩けるので、`_common.sh` の `notion_curl` を subprocess で呼ばない。
2. **呼び出し側のスキルは、独自の薄いラッパー（`_notion_client.py` など）を持たない。** 操作単位の入口は `notion_client.py` に1つだけ置く。
3. **呼び出し側で `time.sleep` もリトライも書かない。** レート制限と一時的な失敗の再試行は `notion_client.py` が引き受ける。
4. **400・404などは再試行しない。** 即座に例外を上げる。
5. **エラーは `sys.exit` せず例外（`NotionError` とその派生）で返す。** コマンドラインのスクリプトは `NotionError` を捕まえて exit する。
6. **`append_block_children` に渡すのは100件まで。** 何件ずつどこで区切るかは呼び出し側が決める。ここでは自動で分割しない。
7. **REST でdate型のプロパティを書くときは、公式の標準形式を使う。** `{"プロパティ名": {"date": {"start": "2026-07-20", "end": null}}}`。公式MCPが使う疑似キー `"date:プロパティ名:start"` はRESTでは通らない。

## 道具

`notion_client.py`（`notion_request` と操作別の関数）。

**値（リクエストの最小間隔・再試行の回数と対象のステータス・APIのバージョン）は、`notion_client.py` の定数が正。** どれもNotion APIという共有する環境の仕様に合わせた値で、作成者の視点ではないので、判断ファイルには置かない。

## 理由

1. （原因）数百件をsubprocessで回すと、`bash`/`uv` のプロセス起動と一時ファイル生成が件数分積み上がり、純オーバーヘッドだけで数分かかる。2026-08-08に、276件をsubprocessで回して起きた。
2. （根拠）同じ関数がスキルの数だけ増え、認証・APIのバージョン・レート制限・エラー処理がそこに散らばる。
3. （根拠・知見）呼び出し側でも待つと、二重に待つことになる。Notion REST APIのレート制限は、Business・Enterprise 以外のプランで平均3リクエスト/秒、Business・Enterprise で平均10リクエスト/秒（出典：Notion 公式ドキュメント「Request limits」。2026-10-23に確認）。
4. （根拠）投げ直しても同じ結果になる。再試行で覆い隠すと、呼び出し側の誤りの発見が遅れる。
   - （原因）再試行を入れたのは、2026-08-30の移行中に、Notion側の503（`Public API object rendering exceeded the response time budget`）と読み取りタイムアウトで2度落ちたため。2,000件超の書き込みの最中に起きると「どこまで書けたか分からない」状態になる。
5. （根拠）呼び出し側が、リトライするか中断するかを選べるようにするため。
6. （知見）APIの1リクエストの上限。ブロックを含む配列は100要素まで（出典：Notion 公式ドキュメント「Request limits」。2026-10-23に確認）。101件以上は、APIに投げる前に `ValueError` で止める。
7. （原因）2026-07-22の動作確認で、疑似キーを送ってバリデーションエラーになった。

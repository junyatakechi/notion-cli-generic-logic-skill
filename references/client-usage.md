# APIの呼び方

## 扱うこと

Notionを読み書きするコードを書くとき、どの入口から呼び、何を呼び出し側で書かないか

## 答え方と理由

### 0. 判断全体

なし

### 1. Pythonからはimport、シェル・他言語からは `scripts/`

Pythonから使うなら常にimport、シェル・他言語からなら `scripts/`。 数百件を一度に読み書きする用途でも、シェルのスクリプトを繰り返し起動しない。操作別の関数に無いエンドポイントも `notion_request` で叩けるので、`_common.sh` の `notion_curl` を subprocess で呼ばない。

1. （原因）数百件をsubprocessで回すと、`bash`/`uv` のプロセス起動と一時ファイル生成が件数分積み上がり、純オーバーヘッドだけで数分かかる。276件をsubprocessで回して起きた。（発生日：2026-08-08）

### 2. 独自の薄いラッパーを持たない

呼び出し側のスキルは、独自の薄いラッパー（`_notion_client.py` など）を持たない。 操作単位の入口は `notion_client.py` に1つだけ置く。

1. （根拠）同じ関数がスキルの数だけ増え、認証・APIのバージョン・レート制限・エラー処理がそこに散らばる。（決定日：記録なし）

### 3. 呼び出し側で待たず、再試行しない

呼び出し側で `time.sleep` もリトライも書かない。 レート制限と一時的な失敗の再試行は `notion_client.py` が引き受ける。

1. （根拠）呼び出し側でも待つと、二重に待つことになる。（決定日：記録なし）
2. （知見）Notion REST APIのレート制限は、Business・Enterprise 以外のプランで平均3リクエスト/秒、Business・Enterprise で平均10リクエスト/秒。（出典：S1）

### 4. 400・404などは再試行しない

400・404などは再試行しない。 即座に例外を上げる。

1. （根拠）投げ直しても同じ結果になる。再試行で覆い隠すと、呼び出し側の誤りの発見が遅れる。（決定日：記録なし）
2. （原因）再試行を入れたのは、移行中に、Notion側の503（`Public API object rendering exceeded the response time budget`）と読み取りタイムアウトで2度落ちたため。2,000件超の書き込みの最中に起きると「どこまで書けたか分からない」状態になる。（発生日：2026-08-30）

### 5. エラーは例外で返す

エラーは `sys.exit` せず例外（`NotionError` とその派生）で返す。 コマンドラインのスクリプトは `NotionError` を捕まえて exit する。

1. （根拠）呼び出し側が、リトライするか中断するかを選べるようにするため。（決定日：記録なし）

### 6. `append_block_children` に渡すのは100件まで

`append_block_children` に渡すのは100件まで。 何件ずつどこで区切るかは呼び出し側が決める。ここでは自動で分割しない。

1. （知見）APIの1リクエストの上限。ブロックを含む配列は100要素まで。101件以上は、APIに投げる前に `ValueError` で止める。（出典：S1）

### 7. RESTのdate型は、公式の標準形式で書く

REST でdate型のプロパティを書くときは、公式の標準形式を使う。 `{"プロパティ名": {"date": {"start": "2026-07-20", "end": null}}}`。公式MCPが使う疑似キー `"date:プロパティ名:start"` はRESTでは通らない。

1. （原因）動作確認で、疑似キーを送ってバリデーションエラーになった。（発生日：2026-07-22）

## 道具

`notion_client.py`（`notion_request` と操作別の関数）。

**値（リクエストの最小間隔・再試行の回数と対象のステータス・APIのバージョン）は、`notion_client.py` の定数が正。** どれもNotion APIという共有する環境の仕様に合わせた値で、作成者の視点ではないので、判断ファイルには置かない。

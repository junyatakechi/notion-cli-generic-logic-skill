# selectの選択肢

## 答え方

1. **選択肢の一覧は、差分ではなく「送った集合がすべて」。** 一覧から外した選択肢は消え、その選択肢を持っていた行の値は**エラーも警告もなく空になる。** DDL（`ALTER COLUMN ... SET SELECT(...)`）でも REST の `PATCH` でも同じ。
2. **選択肢を入れ替えるときは、必ずこの順で行う。**
   1. 新しい選択肢を**足すだけ**（古い選択肢は一覧に残したまま）
   2. 行を新しい選択肢へ振り直す
   3. **古い選択肢が0件になったことをクエリで確かめる**
   4. 0件を確かめてから、古い選択肢を一覧から外す
3. **選択肢を改名したいときは、値を書き換える。** 選択肢は書けば自動で生えるので、新しい名前を全行へ書いてから、古い選択肢を一覧から外す。この順番を逆にしない。`select.options` を `id` 付きで渡して名前を書き換えない。黙って捨てられる。
4. **1つの選択肢を直すつもりで、その1件だけを一覧に入れて送らない。** 他の選択肢が全部消える。
5. **一覧に載せ直す既存の選択肢は、現在の色をそのまま書く。** 色を変えたいなら画面で変える。
6. **`ALTER COLUMN "X" SET SELECT(...)` は使わない。** 名前でしか指定できないぶん、書き落とした選択肢の値が黙って消える危険が `PATCH` より高い。
7. 選択肢を変える `PATCH` には、その列の `description` も同送する（[列の説明と改名](column-description.md)）。

## 理由

1. （原因）1行だけ使われている選択肢を一覧から外して実測したところ、その行の値は `None` になった。2026-08-30に2,311件のカテゴリを壊した事故と同じ挙動。
2. （原因）2026-09-13に、あるDBの選択肢の再編で、この順序により数十件を無傷で移行した。逆順だと、外した選択肢を持っていた行が空になる。
3. （原因）**選択肢の改名は通らない。** `select.options` を `id` 付きで渡しても、名前の変更だけが黙って捨てられる（2026-09-14に実測）。先に古い選択肢を消すと、値が空になってから書き直すことになり、途中で止まったとき何が入っていたか分からなくなる。
4. 記録なし
5. （原因）既存の選択肢に違う色を指定すると、`Cannot update color of select with name: <名前>`（`id` 指定なら `with id: <id>`）で400になる。色の重複指定は通るので、移行の途中で新旧が同じ色でも問題ない。消した選択肢を作り直すと、色は自動で割り当て直される（`purple` が `brown` になった）。

| 送ったもの | 結果（2026-09-14に実測） |
|---|---|
| `{"id": 既存, "name": "新しい名前"}` | **無反応**（成功レスポンス・名前は変わらない） |
| `{"id": 既存, "color": "別の色"}` | **400** |
| 一覧から選択肢を**省く** | **その選択肢が消える** |
| 選択肢に無い値を**ページへ書く** | **選択肢が自動で生える** |

色の変更は400を返すので、Notionは一覧を読んで検証している。それでも名前の変更だけはエラーにもならず消える。だから「成功したのに変わっていない」という形でしか気づけない。
6. 記録なし
7. 記録なし

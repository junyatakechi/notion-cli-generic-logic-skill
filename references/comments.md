# コメントの扱い

## 扱うこと

コメントに関わる作業をするとき・コメントの付いた表の行や列を増減させるとき、コメントをどう取り、誰に、どの経路で返信し、スレッドをどう守るか

## 答え方と理由

### 0. 判断全体

準備が足りないときの合図は、この判断では答えない（→ [設定の不足](missing-setup.md)）。

- ここが持つのは取り方と返し方で、何と答えるかは呼び出し側の判断。
- （原因）指示者のIDがMCPでしか取れないのは、MCPコネクタが指示者のNotionアカウントとして認証されているため。返る `id` は、コメントの `user-url` に入っているUUIDと同じもの。（発生日：2026-09-17）
- （原因）RESTの `GET /users/me` はトークンの持ち主であるIntegrationのbotを返す。（発生日：2026-09-29）

### 1. 既定は、取得して内容を伝えるところまで

既定は、取得して内容を伝えるところまで。 どの記述への指摘か・誰の発言かを添えて伝える。「返信して」「答えて」と言われたときだけ返信する。「拾う」は取得だけを指す。

| 言われ方 | すること |
|---|---|
| 「Notionのコメントを拾って」「コメントを拾っておいて」 | 取得 → 内容を伝える（返信しない） |
| 「ページのコメントを見て」「指摘を拾って」 | 取得 → 内容を伝える（返信しない） |
| 「コメントに答えて」「コメントに返信して」「拾って返信して」 | 取得 → 自分宛ての全件へ返信 |

1. （根拠）記録なし。既定を「全件へ返信」から「取得のみ」へ変えた。（決定日：2026-10-01）

### 2. 扱うのは未解決のコメントだけ

扱うのは未解決のコメントだけ。 解決済みは、取得の段階で返ってこない経路だけを使う。

1. 記録なし

### 3. `discussion-urls` をコメントの根拠にしない

公式MCPの `notion-fetch` の本文にある `discussion-urls` は、コメントの根拠にしない。 解決済みのスレッドの箇所にも付くので、未解決のコメントがあるかも件数も分からない。コメントに触れるのは、取得の経路で取ってからにする。

1. （原因）未解決のコメントが0件のページで、`discussion-urls` 属性が9か所に付いていた。推敲を頼まれてページを読んだときに、この属性を数えて「未解決のコメントが8件ある」と伝え、誤りだった。（発生日：2026-10-14）
2. （知見）`include_discussions` を付けなくても、スレッドがアンカーされた見出しや `<span>` に付き、解決済みのスレッドの箇所にも付く。（出典：なし）

### 4. 取得はRESTが既定

取得はRESTが既定。 公式MCPを使うのは、効率を重視するよう頼まれたときだけ。「効率重視で」「急いで」「手早く」のように、速さや手数の少なさを頼まれた場合が当たる。迷ったらRESTにする。 ページが大きいことを理由に、頼まれていないのにMCPへ切り替えない。

1. （原因）2026-09-17から取得はMCPで行っていたが、RESTを既定へ戻した。（発生日：2026-09-29）
2. （根拠）スキルの本分はREST APIへの薄いアクセスにあり、MCPは速さが要る場面の例外にとどめるため。（決定日：2026-09-29）

### 5. 返信するのは、最後のコメントが指示者のスレッドだけ

返信するのは、最後のコメントが指示者のスレッドだけ。
- 取得は全員ぶん返る（他メンバーのコメントも、スレッド内の自分の過去の返信も）。絞るのは取ったあと。
- 判定はスレッド単位で、最後のコメントを見る。
- スキルにも設定ファイルにも、メールアドレスやユーザーIDを書かない。
- 一致する発言でも、内容を書いたのが指示者とは限らない。公式MCPで投稿すると指示者名義になるため（→ 答え方6の理由1）、過去にその経路で返した返信は人の発言として返る。

| スレッドの最後のコメント | 扱い |
|---|---|
| 指示者 | 返信する（自分の問いかけが未応答） |
| bot | 飛ばす（返信済み） |
| 他のメンバー | 飛ばす（自分宛てとは限らない。答えるなら指示者の指示が要る） |

- 返信を頼まれたら、自分宛てのスレッド（→ 答え方5）全件へ返す。答えが決め切れないスレッドも飛ばさず、分かる範囲の回答と、確認したい点を書いて返す。取得した `discussion_id` を先に全部並べてから回す。 1件読んでは考え…と進めると、途中で「残りはどうしますか?」と聞き返して打ち切りやすい。

1. （根拠）他のメンバーのスレッドは、自分宛てとは限らない。最後がbotのスレッドは、返信済み。（決定日：記録なし）

### 6. 返信は例外なくREST

返信は例外なくREST。 公式MCPの `notion-create-comment` は使わない。

1. （原因）公式MCPコネクタは指示者のNotionアカウントとして投稿するので、Claudeの返信が指示者の発言として残る。他スキル経由の実行で実際に起きた。（発生日：2026-09-17）

### 7. 表の行・列を増減させる前に、返信を済ませる

コメントの付いた表の行・列を増減させる前に、頼まれている返信を済ませる。 先に返信しておけば、ブロックが作り直されても返信は残る。表を直したあとで消えたことに気づいたら、同じ節へページコメントを立て直し、「元のスレッドが消えた」と明記する。 黙って新しいスレッドにすると、相手は自分の指摘が無視されたように見えるため。セル1つの文言を直すだけなら消えない。 消えるのは行数・列数が変わるときと、表全体を置換したとき。

1. （原因）`notion-update-page` の `update_content` は、表のように行を持つブロックを書き換えるとき、ブロックごと作り直す（新しいblock_idになり、古いIDは404）。そのブロックにアンカーされたスレッドは、返信する前に消える。ある表へ列を1つ足しただけでスレッドが1件消えた。`discussion_id` は取得済みだったが、`POST /comments` を投げる前に対象が無くなっていた。（発生日：2026-09-17）

### 8. 終わったら、件数を報告する

終わったら、取得件数（返信したときは返信件数も）を報告する。

1. （根拠）数が合わなければ、取りこぼしている。（決定日：記録なし）

### 9. 取得に `notion-fetch` を使わない

コメントの取得に `notion-fetch(include_discussions=true)` を使わない。

1. （原因）本文にアンカーの出ないコメント（Mermaid図など）を取りこぼすうえ、ページ本文を丸ごと読む。同じページで実測して fetch=5件 / get-comments=9件だった。（発生日：記録なし）

### 10. APIでできることと、できないこと

APIでできることと、できないことは次のとおり。

| やりたいこと | 可否 |
|---|---|
| 既存スレッドへ返信 | ○ |
| ページ・ブロックへコメント | ○ |
| 選択したテキスト範囲に新しいスレッドを立てる | × |
| コメントを解決する | ×（画面で行う） |
| コメントが付いた文字範囲をRESTで知る | ×（ブロック単位まで。MCPの `text-context` なら分かる） |

1. 記録なし

## 道具

`get_comments`・`create_comment`・`notion_request`（`notion_client.py`）と、公式MCPの `notion-get-comments`・`notion-get-users`。

| 経路 | 解決済みを除く方法 |
|---|---|
| REST `get_comments` | 何もしなくてよい。APIが未解決しか返さない |
| MCP `notion-get-comments` | **`include_resolved` を渡さない**（省略で未解決のみ）。`true` にしない |
| MCP `notion-fetch(include_discussions=true)` | 使わない（→ 答え方の9） |
| MCP `notion-fetch` の本文の `discussion-urls` 属性 | 除けない。コメントの根拠にしない（→ 答え方の3） |

公式MCPを使うのは下の2つだけで、どれもRESTでは代わりが効かない。

| 場面 | 使うMCPのツール | RESTで済ませない理由 |
|---|---|---|
| **コメントの取得で、効率を重視するよう頼まれたとき** | `notion-get-comments` | RESTはブロック単位でしか返さず、ページ全体ではブロック数ぶん問い合わせる（228ブロックで約2分） |
| 返信するスレッドを絞るため、指示者のIDを知るとき | `notion-get-users(user_id="self")` | RESTのトークンはIntegrationなので、`GET /users/me` はbotを返す |

### 答え方4：未解決スレッドを取る（既定）：REST `GET /comments`

```python
from notion_client import page_id_from_url, get_comments

page_id = page_id_from_url("<ページURL>")
comments = get_comments(page_id, recursive=True)
```

- **`recursive=True` を付ける。** 付けないとページ自体へのコメントだけが返り、本文への
  インラインコメントが落ちる。`GET /comments?block_id=` はそのブロック単位でしか返さないため、
  `get_comments` が本文の全ブロックを辿って1つずつ問い合わせる（子ページは辿らない）
- **時間はブロック数で決まる。** 1ブロック＝1リクエストで、待ちは `notion_request` が見る
  （2026-09-17の実測: 228ブロックで約2分）。呼び出し側で並列化や `time.sleep` を足さない
- 返る各コメントのうち、使うのは次の4つ

| フィールド | 中身 |
|---|---|
| `discussion_id` | スレッドのID。**返信に使う** |
| `parent` | どこへのコメントか。本文なら `block_id`、ページ自体なら `page_id` |
| `created_by` | **`id` と `object` だけ**。人かbotかは `id` を突き合わせて判定する（→ 答え方5） |
| `rich_text` | コメント本文 |

- **どの記述への指摘かは、ブロック単位までしか分からない。** 選択範囲の文字列は返らないので、
  `notion_request("GET", f"/blocks/{block_id}")` で対象ブロックを取り、`notion_blocks.block_to_lines`
  で本文を読む。範囲まで要るならMCPの `text-context`（→ 下の MCP の節）

### 答え方4：未解決スレッドを取る（効率を重視するよう頼まれたとき）：MCP `notion-get-comments`

```
notion-get-comments(page_id="<page ID>", include_all_blocks=true)
```

- **1回の呼び出しでページ全体が取れる。** RESTのようにブロック数ぶん問い合わせない
- **`include_resolved` は渡さない。** 省けば未解決のみが返る。`true` にすると解決済みまで返り、
  読まなくてよいものを読むことになる
- **`include_all_blocks: true` を必ず付ける。** 既定はページ直下のスレッドだけで、インラインコメントが落ちる
- **`page_id` はUUIDのみ。** ページURLを渡すと400になるので、URL末尾の32桁を `8-4-4-4-12` へ整形してから渡す。
  指示者はURLを貼るだけでよい
- 返る `discussion://<ページID>/<ブロックID>/<discussionID>` の**末尾が `discussion_id`**。これを返信に使う。
  `text-context` にアンカーされた本文が入るので、どの記述への指摘かはこれで分かる

| | REST `get_comments`（既定） | MCP `notion-get-comments`（例外） |
|---|---|---|
| ページ全体を取る | 本文の全ブロックを1つずつ問い合わせる | 1回 |
| 時間 | ブロック数に比例（228ブロックで約2分） | ほぼ一定 |
| 解決済み | 返らない | `include_resolved` を渡さなければ返らない |
| どの記述への指摘か | ブロック単位まで | 選択範囲の文字列（`text-context`）まで |
| 投稿者の見分け方 | `created_by.id` | `user-url` |

### 答え方5：自分宛てのスレッドを見分ける

投稿者で絞るパラメータは、RESTにもMCPにも無い。突き合わせる相手は2つで、どちらも1回引いて使い回す。

| 誰 | 取り方 |
|---|---|
| 指示者 | MCP `notion-get-users(user_id="self")` の `id` |
| このスキルのbot（過去の返信） | REST `notion_request("GET", "/users/me")` の `id`（`type` は `"bot"`） |

スレッドの最後のコメントは、RESTなら `discussion_id` でまとめ、`created_time` が最も新しいもの。

| スレッドの最後のコメント | RESTでの見分け方 | MCPでの見分け方 |
|---|---|---|
| 指示者 | `created_by.id` が `self` の `id` と一致 | `user-url` が `user://<self の id>/<メール>` |
| bot | `created_by.id` が `/users/me` の `id` と一致 | `user-url` が `bot` |
| 他のメンバー | どちらとも一致しない | `self` と違うUUID |

### 答え方6：返信する：REST `POST /comments`

```python
create_comment({
    "discussion_id": "<discussion ID>",
    "rich_text": [{"text": {"content": "ご指摘の…"}}],
})
```

| 経路 | 認証 | 投稿者 |
|---|---|---|
| REST `create_comment`（`notion_client.py`） | Integrationトークン | **bot**（Integration名）← これで返す |
| MCP `notion-create-comment` | 使い手のNotionアカウント | **指示者** ← 使わない |

- **1スレッド＝1リクエスト。** 複数スレッドに答えるならこれを件数ぶん呼ぶ（待ちは `notion_request` が見る）
- **投稿者はIntegrationのbot**（`created_by` は `type: "bot"`）。`display_name` を付けても
  **表示名が変わるだけ**で `created_by` はbotのまま。既定（Integration名）で使う。
  **レスポンスの `created_by.type` が `"bot"` かで、botとして入ったことを確かめられる**
- **見分け方は投稿者名。** 返信後にNotionで自分の名前とアイコンが付いていたら、MCPで投げている
